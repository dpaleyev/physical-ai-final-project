# Как проверить финальный проект

Это закрытая инструкция для проверяющего. Студенты получают отдельный архив без
папки `reviewer/` и истории репозитория. Не передавайте им параметры advanced-сцен.

Студент выбирает одну пару «робот + задача» из восьми доступных сочетаний.
Для неё он обучает RL-эксперта, собирает данные, обучает BC, сравнивает варианты
модели и исследует робастность. Другие пары в сдаче не требуются.
Ваша задача — проверить, что эти этапы выполнены, воспроизвести оценку моделей
и сопоставить результаты с выводами студента.

## 1. Проверьте комплект сдачи

Попросите студента передать одну папку со следующими материалами:

- `submission.json`, заполненный по `submission.example.json`;
- отчёт по `REPORT_TEMPLATE.md` и команды воспроизведения;
- одну PPO-модель `.zip` и JSON-файл с её настройками;
- для той же пары — три BC-модели `.ts` с JSON-файлами:
  RGB-baseline, RGB + проприоцепция, модель с аугментациями;
- датасеты LeRobot v3 либо доступные ссылки на них, логи обучения и несколько видео.

В `models` должна быть ровно одна запись с выбранными `robot` и `task`.
Все пути в `submission.json` считаются относительно самого файла. JSON с
метаданными должен лежать рядом с моделью и иметь то же имя до расширения.
Например: `best.ts` и `best.json`. Если чего-то нет, сначала запросите недостающее.

## 2. Запустите автоматическую проверку

Используйте этот репозиторий и окружение из корневого README. Так все сдачи будут
проверяться на одинаковой физике, независимо от изменений среды у студента.

Сначала убедитесь, что файлы загружаются и модели возвращают допустимые действия:

```bash
MUJOCO_GL=osmesa python -m reviewer.grade /path/to/submission.json \
  --out runs/grading/student_01/smoke --episodes 1 --max-steps 2
```

Откройте `runs/grading/student_01/smoke/results.json`. Поле `error` означает
техническую проблему: отсутствующий файл, несовпадение робота или неправильный
интерфейс модели. Это не нулевое качество — попросите студента исправить сдачу.
За два шага робот не обязан решить задачу.

После успешной загрузки выполните полную оценку:

```bash
MUJOCO_GL=osmesa python -m reviewer.grade /path/to/submission.json \
  --out runs/grading/student_01/full --episodes 50 --seed 738921 --video
```

Для остальных студентов меняйте каталог результатов, сохраняя одинаковый seed.
Полная проверка — 400 эпизодов: 1 пара × 4 модели × 2 набора сцен × 50 запусков.
Она может занять много времени. Не уменьшайте горизонт 1000 шагов в итоговой оценке.

Результаты находятся в указанном каталоге:

| Файл | Что смотреть |
|---|---|
| `summary.csv` | Доля успехов (`success_rate`) для каждой модели на base и advanced |
| `results.json` | Исход каждого эпизода, seed, число шагов, ошибки запуска |
| `videos/` | Первый эпизод каждой конфигурации, если указан `--video` |

`success_rate = 0.8` означает 80% успешных эпизодов. Главные сравнения:
BC против RL на base; BC с проприоцепцией против RGB-baseline; робастная BC против
той же BC без аугментаций на advanced. При этом проверьте, не ухудшилась ли base.

В JSON также есть `wilson_95`: 95%-й доверительный интервал для доли успехов.
Он показывает неопределённость оценки по ограниченному числу эпизодов: даже 50/50
не доказывает, что модель будет успешна всегда. Программа считает его сама;
отдельных баллов за этот показатель нет. Для чтения основной таблицы достаточно
доли успехов и числа эпизодов.

## 3. Что меняется в advanced

Base использует известные студентам сцены. Advanced сохраняет задачу и критерий
успеха, но меняет детали сцены. Внутри каждого набора сравниваемые модели получают
одинаковые изменения. Проверяется только выбранная студентом пара; из таблицы
ниже применяется соответствующая ей строка. Правила реализованы в `scenarios.py`.

| Задача | Изменение в закрытом тесте | Что остаётся обязательным |
|---|---|---|
| Чашка → тарелка | Чашка становится вытянутой: масштаб по X 1.10–1.18, по Y 0.87–0.94; высота сохранена | Захватить, перенести и отпустить чашку в тарелке |
| Кружка → подставка | Опора выше или ниже: UR5e на 2–3.5 см, KUKA на 1–2 см | Кружка устойчиво стоит на опоре, захват отпущен |
| Перенос рядом с соседней кружкой | Обе кружки начинают в других местах: переносимая смещена по X до 2.5 см и по Y до 2 см; соседняя — в области X 0.60–0.67 м, Y −0.025–0.035 м | Перенести первую, не сдвинув соседнюю более чем на 2 см от её фактического положения после reset |
| Выбор тарелки по цвету | Новая палитра из оранжевого, фиолетового и бирюзового; два цвета случайно назначаются тарелкам, кружка получает один из них | Выбрать тарелку по совпадению цвета с кружкой |

Для KUKA базовая подставка ниже, чем для UR5e. Закрытые смещения заданы относительно
своей исходной сцены. Для цвета одного постоянного выбора левой или правой тарелки
недостаточно. Форма чашки меняется в физической геометрии, а не только на картинке.

Эти конкретные изменения и диапазоны не выдаются студентам. Они самостоятельно
выбирают аугментации, используя общий API изменения сцены.

## 4. Прочитайте отчёт и проверьте эксперименты

Автоматический запуск проверяет модели, но не заменяет проверку работы студента.

| Этап | Что должно быть в отчёте и артефактах |
|---|---|
| RL | Эксперт выбранной пары, настройки, кривые и оценка на обычном reset; сравнение двух настроек |
| Данные | Сбор действиями обученного PPO; число попыток и успешных эпизодов; разделение train/val целыми эпизодами |
| BC | RGB-baseline и BC с проприоцепцией для выбранной пары на одинаковых данных; сравнение с RL |
| Абляция | BC с проприоцепцией на 25% и на 100% демонстраций для выбранной пары; по одному обучению с одним seed |
| Робастность | Не менее трёх типов изменений сцены, оценка исходной BC, одна BC-модель с аугментациями и повторная оценка |

Дополнительно проверьте три вещи. Во-первых, SHA256 эксперта в `meta/provenance.jsonl` каждого LeRobot-датасета
должен совпадать с использованной PPO-моделью. Во-вторых, эпизоды train и val не
должны пересекаться. В-третьих, BC получает только изображение и, в соответствующем
варианте, проприоцепцию; координаты предметов и целей из симулятора ей недоступны.

Попросите объяснить неудачи по нескольким видео. Снижение ошибки предсказания
действий (MSE) само по себе не доказывает улучшение поведения робота. Если улучшенная
BC получила больше данных, в отчёте нужен контрольный эксперимент с таким же
объёмом данных без аугментаций.

Повторять обучение с разными seeds не требуется, в том числе в абляции.
Не снижайте баллы за отсутствие таких повторов. Проверка на 50 эпизодах остаётся
обязательной: это запуск готовой модели в разных начальных условиях.

Готовые curriculum, перенос весов, признаки и настройки действий предоставлены
в шаблоне. Рецепт выбранной пары может автоматически обучать промежуточные модели
других пар для переноса весов. Их отдельная сдача, сбор данных и BC не требуются.
Студент не обязан заново изобретать эти приёмы. Оценивайте запуск обучения,
понимание предоставленной помощи и самостоятельные эксперименты. Действия
скриптового контроллера не заменяют демонстрации обученного PPO.

## 5. Выставьте баллы и напишите обратную связь

| Раздел | Максимум | За что ставить баллы |
|---|---:|---|
| RL | 25 | Обучен и оценён эксперт выбранной пары; есть настройки, логи и сравнение |
| Данные | 15 | Данные действительно собраны PPO, происхождение и разбиение проверяемы |
| BC и сравнения | 25 | Два основных варианта BC для выбранной пары, сравнения и абляция объёма данных |
| Робастность | 25 | Осмысленные вариации, обучение с аугментациями и корректное сравнение |
| Воспроизводимость | 10 | Рабочие файлы, команды, версии и понятный отчёт |

В каждом разделе ориентируйтесь на полноту: 0% — этап отсутствует; 50% — выполнен
частично; 75% — есть небольшие пробелы; 100% — все требования подтверждены.
Напишите по одному короткому объяснению выставленных баллов.

Для готовности RL к сбору данных требуется не менее 40 успехов из 50 на base
для выбранной пары. В задаче цвета дополнительно проверьте успехи отдельно по двум
целям (`goal_slot` в эпизодах `results.json`): для каждой нужна доля не ниже 80%.
Для BC и advanced фиксированного проходного SR пока нет: оценивайте полноту
экспериментов и обоснованность выводов. Отрицательный результат аугментаций сам
по себе не означает ноль баллов, если эксперимент проведён корректно.

Рекомендуемый проходной балл — 60/100 при выполнении всех пяти этапов проекта.
Организаторы должны утвердить эту рубрику до выдачи задания. Подмена RL скриптом,
доступ BC к скрытому состоянию или пересечение train/test требуют доработки
соответствующего этапа, даже если показан высокий SR.

В ответе студенту укажите баллы по разделам, основные результаты base/advanced
и конкретный список того, что нужно исправить. Параметры закрытых сцен не раскрывайте.

## Организатору перед выдачей

Экспортируйте студенческую версию из корня репозитория:

```bash
python -m reviewer.export_students dist/physical-ai-student --zip
```

Для организаторов сохранены восемь эталонных PPO-экспертов, чтобы покрыть любой
выбор студента. Это не требование выполнить восемь задач. Каждый эксперт уже
проверен по 50 обычным эпизодам:

| Задача | UR5e | KUKA |
|---|---:|---:|
| Чашка → тарелка | 50/50 | 50/50 |
| Кружка → подставка | 49/50 | 50/50 |
| Перенос рядом с соседней кружкой | 50/50 | 50/50 |
| Выбор тарелки по цвету | 50/50 | 47/50 |

Их оценки, настройки и происхождение данных сохранены в `evidence/calibration/`;
сводка — `evidence/learning_calibration.json`. Модели и 200 успешных демонстраций
находятся в приватном архиве релиза. Короткие BC-пилоты обучены всего на 20 train
и 5 val эпизодах, 3 эпохи до обновления формата данных: они подтверждают работу прежнего
пайплайна, но не задают проходной уровень BC. Все 200 демонстраций переведены
в LeRobot v3 с точным сохранением действий и состояний; отдельно выполнено
по одной эпохе BC на новых данных для каждой пары. Эти новые запуски проверяют
совместимость формата, а не качество робастности. Запись нового успешного
эпизода PPO сразу в LeRobot также проверена. Доказательства миграции —
`evidence/lerobot_migration.json` и `evidence/lerobot_native_collection.json`. Повторная полная сходимость PPO на другом оборудовании
не измерялась; рецепт не обещает идентичные веса. До выдачи оцените его время
на оборудовании студентов для выбранного `--target`. Весь рецепт для восьми
эталонов содержит 10.33 млн запрошенных переходов, но студент запускает только
необходимые для своей пары стадии.

Если меняете сцены или закрытые диапазоны, сначала выполните
`MUJOCO_GL=osmesa python -m reviewer.check_scenes --out runs/physical_checks.json`.
Это проверка физической выполнимости контроллером, не оценка обученной политики.
