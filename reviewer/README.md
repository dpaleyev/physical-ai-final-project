# Проверяющим и организаторам — закрытая часть

Не распространяйте эту папку, содержимое `docs/superpowers`, приватную git-историю
или результаты advanced-проверки до окончания сдачи. Студенческая версия создаётся
`python -m reviewer.export_students dist/physical-ai-student --zip`.
Публичное задание сообщает лишь об отложенных вариантах сцен и общем API правок.

## Что подготовлено и что проверять перед выдачей

Прочитайте `VALIDATION.md`: там раздельно приведены независимая оценка RL,
сквозная проверка на настоящих PPO-демонстрациях и ограничения короткого BC-пилота.
Все четыре задачи требуют одного переноса. Используйте поставляемый рецепт
`configs/ppo_calibrated.json`; прямой PPO без curriculum — отдельный исследовательский
вариант, а не подтверждённый способ быстро получить эксперта.

Рецепт содержит состояния, физически достигнутые контроллером в **base-сценах**.
Они используются только для reset во время обучения, без обучения по действиям
контроллера. Это явная предоставленная помощь, описанная студентам. Эксперты
обучаются PPO; оценка и сбор демонстраций начинаются с обычного reset. В рецепте
нет advanced-сцен, их параметров или seeds. Перед потоком измерьте время на
оборудовании студентов и согласуйте доступный вычислительный бюджет.

Внутренний `physical_probe.py` использует детерминированный контроллер с точным
состоянием. Он предназначен для проверки контактов, достижимости и освобождения
предметов, не выдаётся студентам и не считается RL-политикой. В рабочем сборщике
демонстраций нет пути, который подменяет PPO этим контроллером.

## Закрытые сценарии

`scenarios.py` детерминированно генерирует вариацию по seed. Конкретные правила
остаются только здесь:

| Задача | Изменение |
|---|---|
| cup_plate | иное поперечное сечение чашки при той же высоте |
| cup_shelf | вертикальное смещение опорной поверхности |
| cup_distractor | небольшие смещения переносимой и соседней кружек; соседнюю по-прежнему нельзя сдвигать |
| color_match | два цвета из новой палитры, случайное назначение тарелкам; одна кружка получает один из этих цветов |

Форма чашки меняет физическую геометрию, а не только картинку. В `color_match`
цель выводится из текущих цветов; постоянный выбор одной тарелки не решает задачу.
Для `cup_distractor` запрет смещения соседней кружки отсчитывается от её фактической
позиции после reset и действует весь эпизод.

Две исходные многоэтапные задачи (обмен кружек и сортировка трёх кружек) заменены
по согласованию с заказчиком: они требовали около 810–855 управляющих шагов
даже от физического скриптового контроллера. Новые задачи сохраняют отвлекающий
объект и выбор цели по цвету, но требуют только одного захвата и освобождения.
Для KUKA высокая опора второй задачи заменена на низкую подставку: базовая
поверхность находится на z=0.454 м. У UR5e сохранена опора z=0.554 м. Закрытые
смещения теперь зависят от робота: KUKA ±1–2 см, UR5e ±2–3.5 см; размеры ножек
согласуются с поверхностью стола. Эти подробности остаются в закрытой части.
Диапазоны лежат в `scenarios.py`. Перед изменением диапазонов проверьте физическую
выполнимость для обоих роботов. Нельзя оценивать робастность на недостижимых задачах.

## Запуск проверки сдачи

Студент передаёт `submission.json`, отчёт и указанные артефакты. Все пути относятся
к каталогу сдачи. Для BC оценщик принимает экспортированную модель `.ts` и её JSON;
архитектура может быть другой, если соблюдён интерфейс из задания. Для RL нужен
PPO `.zip` с JSON и контрольной суммой. Восемь уникальных пар обязательны.

```bash
# Из корня организаторского репозитория, в его исходном окружении:
MUJOCO_GL=osmesa python -m reviewer.grade /path/to/submission.json \
  --out runs/grading/smoke --episodes 1 --max-steps 2
MUJOCO_GL=osmesa python -m reviewer.grade /path/to/submission.json \
  --out runs/grading/full --episodes 50 --seed 738921 --video
```

Первая команда проверяет интерфейсы, не качество. Вторая оценивает RL, RGB-baseline,
BC+proprio и BC+аугментации во всех восьми средах, отдельно base/advanced. Один seed
соответствует одному reset; advanced-параметры дополнительно меняются между эпизодами.
Сравниваемые модели получают одинаковые seeds и сценарии.

Оценщик использует код и физику организатора, а не изменённую среду студента.
Ошибка одной модели записывается в отчёт, проверка остальных продолжается;
итоговый exit code ненулевой при любой технической ошибке. Не интерпретируйте
ошибку загрузки как нулевой success rate.

Выход: подробный `results.json` и `summary.csv`; при `--video` — первый эпизод
каждой конфигурации. Сохраняйте их приватно. Для разбора остальных неудач повторите
оценку конкретного seed с видео. Интервалы Wilson характеризуют вариативность
эпизодов, не заменяют сравнения нескольких seeds обучения.

Оценка 8×4×2×50 эпизодов ресурсоёмка. Измерьте скорость на одном варианте,
зарезервируйте время; EGL с рабочим GPU-драйвером ускоряет рендер. `--max-steps`
нельзя сокращать в итоговой проверке относительно объявленного горизонта 1000.

## Рубрика: 100 баллов

| Раздел | Баллы | Доказательства |
|---|---:|---|
| RL и адаптация | 25 | 8 экспертов; RL-обновления, конфиги/кривые, независимые rollout, сравнение настроек |
| Данные | 15 | сбор именно RL-политиками, provenance, эпизодное разбиение, контроль качества |
| BC и сравнения | 25 | вся матрица, RGB/proprio, сравнение с RL, абляция данных, корректные бюджеты/seeds |
| Робастность | 25 | собственные вариации, контрольные эксперименты, 8 моделей с аугментациями, обоснованные выводы |
| Воспроизводимость | 10 | рабочие артефакты, команды, версии, отчёт и диагностические видео |

Для каждого раздела: 0% — нет результата; 50% — частично воспроизводится или
существенно неполная матрица; 75% — выполнено с локальными пробелами; 100% — все
требования подкреплены артефактами и выводами. Баллы округляйте до целого и
сопровождайте коротким объяснением. Рекомендуемый проходной уровень — 60/100 при
выполнении всех пяти формальных чекпоинтов; окончательно утвердить после пилота.

Для готовности RL-эксперта к сбору данных используйте **SR ≥80% на 50 обычных
base-эпизодах** для каждой пары; в `color_match` обе цели должны по отдельности
достигать этого порога. Зафиксируйте порог до выдачи задания и применяйте одинаково
ко всем студентам. Качество BC и advanced оценивайте вместе с экспериментальным
анализом; короткий BC-пилот не калибрует проходной SR этих моделей.
Отсутствующий RL-этап, подмена эксперта скриптом, доступ BC к скрытому состоянию или
утечка train/test — основания вернуть соответствующий этап на доработку.
Отрицательный результат робастности сам по себе не обнуляет раздел: оценивайте
корректность эксперимента, его полноту и качество объяснения.

## Ручная проверка

- Сопоставьте SHA256 RL-файлов с метаданными демонстраций, проверьте логи обучения.
- Проверьте реальные размеры наборов и отсутствие общих reset/эпизодов в splits.
- Выбор checkpoint и гиперпараметров должен предшествовать закрытому тесту.
- При сравнении с RL учтены разные входные наблюдения.
- Дополнительные данные/вычисления отделены от эффекта аугментации.
- Для абляций предъявлены независимые training seeds, а не три повторных rollout
  одного и того же checkpoint.
- Готовые baseline-файлы без самостоятельных экспериментов не являются завершённой работой.

## Учебный пилот

```bash
python -m physical_ai.train_curriculum --recipe configs/ppo_calibrated.json \
  --target ur5e/cup_plate --out runs/reproduction
# Аналогично остальные 7 целей с тем же --out.
MUJOCO_GL=osmesa python -m reviewer.validate_expert \
  --robot ur5e --task cup_plate \
  --checkpoint runs/reproduction/experts/ur5e/cup_plate/last.zip \
  --out runs/validation/ur5e_cup_plate --seed 100000
```

Валидатор сначала проводит 50 обычных rollout, затем сохраняет 20 успешных PPO
эпизодов train и 5 val, запускает 3 эпохи BC и 5 его полных rollout. Это проверка
пригодности эксперта и всего пайплайна; для исследования качества BC нужны большие
бюджеты из задания. Используйте новый output-каталог, не перезаписывайте результат.

Старый `reviewer.pilot` оставлен для независимых экспериментов с прямым PPO без
банка состояний; не используйте его как замену проверенному рецепту. Отрицательные
исторические результаты сохранены в `evidence/`, чтобы не смешивать их с новой
калибровкой. Промежуточные reset-состояния и перенос весов учитывайте в вычислительном
бюджете, происхождении политики и отчёте.
