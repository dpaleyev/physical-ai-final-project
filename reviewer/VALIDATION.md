# Фактическая валидация

Дата: 2026-09-29. Linux x86_64, Python 3.12.3, 24 логических CPU, 61 GiB RAM.
MuJoCo 3.3.7, PyTorch 2.7.1+cpu, SB3 2.7.0, рендер OSMesa. GPU не использовалась.
Зависимости закреплены в `requirements-lock.txt`.

## RL: независимая оценка полной задачи

Каждая итоговая политика прошла не менее 50 обычных reset в `ManipulationEnv`,
без curriculum, скриптовых действий и изменения состояния во время rollout.
Горизонт — 1000 управляющих шагов. Seeds этой оценки не использованы для PPO,
промежуточного выбора стадий, сбора train/val или BC. Для выбора цвета отдельно
проверены обе цели. Контрольные суммы checkpoints, версии среды и подробные
эпизоды сохранены в `evidence/calibration/` и приватном архиве релиза.

**BC-столбец — короткая проверка пайплайна, не результат полного учебного проекта.**
Для каждого эксперта фактически собраны успешные PPO-демонстрации с RGB и
проприоцепцией, проверены происхождение и отсутствие общих эпизодов между splits.
На них обучены BC-модели с проприоцепцией: 3 эпохи, затем TorchScript и 5 полных
rollout. Нулевой SR такого BC-пилота не скрывается. Для качества BC нужны больший
датасет, настройки и сравнения из задания; они остаются работой студента.

## Как получены эксперты

Готовый рецепт — `configs/ppo_calibrated.json`; он воспроизводит использованные
стадии и общие зависимости, а не запускает заново все неудачные исследования.
Воспроизведение выполняется текущим кодом; битовая идентичность историческим
checkpoint не заявляется. Исходные environment/scene/reward версии стадий
сохранены в reference_code; не записанные тогда хэши trainer/policy обозначены null.
Банки привязаны к хэшу конкретного MJCF с нормализованным корнем проекта.
При обновлении подставки KUKA хэши остальных семи сцен сверены с исходными;
их состояния и ранее собранные данные не изменялись. Метаданные экспортированных
банков дополнены model_sha256 и source_bank_sha256 с проверкой исходной версии.
Всего 162 уникальных стадий, 10,330,000 запрошенных PPO-переходов.
Фактическое число округляется вверх до размера rollout. Метаданные каждой стадии
содержат настройки, хэш банка и исходного checkpoint, а также ненулевое изменение
параметров после PPO-обновлений. Время воспроизведения зависит от оборудования;
стадии одной цепочки последовательны, общие стадии переиспользуются.

Банки reset-состояний созданы физическим контроллером в base-сценах. Это явный
дополнительный prior, **не RL с нуля без помощи**. Контроллер не предоставляет
обучающие действия: PPO взаимодействует с физикой после reset и обучается по
награде. Студенческая инструкция описывает эту помощь; закрытых сценариев в банках
нет. Итоговые демонстрации собраны непосредственно обученными PPO-политиками.

UR5e использует ограниченное среднее действие и gSDE. Для KUKA сначала перенесены
признаки рабочего пространства с заменой суставных входов, затем выполнены свои
PPO-обновления. У политик KUKA среднее XYZ масштабировано на 0.25; команда пальцев
сохраняет полный диапазон. Интерфейс среды и физика не переключаются по политике.

## Исправления и отрицательные результаты

Две многоэтапные исходные задачи заменены на один перенос рядом с другой кружкой
и выбор одной из двух тарелок по цвету. Advanced согласован с ними в `scenarios.py`.
Для KUKA исходная высокая опора заменена на низкую подставку (surface z=0.454 м);
UR5e сохраняет исходную опору (z=0.554 м). Новая политика KUKA прошла отдельное
PPO-дообучение из своего plate-эксперта; изменения веса измерены после инициализации.
Закрытые варианты согласованы с новой геометрией. Эти диапазоны не выдаются студентам.
У учебных чашек добавлены физические крышки: пальцы больше не цепляются за внутреннюю
полость. Крышки видимы в восьми XML и изображениях; weld-приклеивания нет.

Награда v3 добавляет потенциал отпускания и отвода захвата. Discounted shaping
сохраняет общий gamma=0.995 и обнуляет потенциал при настоящем terminal, но не при
time-limit truncation. Regression защищает предпочтение завершения ожиданию.

Критерий `success_version=2` исправляет ошибку задачи с соседней кружкой: ранее
контактная угловая вибрация неподвижной соседней кружки могла отклонить правильный
перенос. Для неё сохранены ограничение XY ≤2 см за весь эпизод и конечные допуски
по высоте/ориентации. Требования к скорости, отпусканию и отводу руки применяются
к переносимой кружке. Ошибка воспроизведена тестом до исправления; оба эксперта
этой задачи затем заново обучены из своих plate-checkpoints и независимо оценены.

Исторические прямые PPO-пилоты v1/v2 давали 0/50 и 0/20; ранний перенос UR5e→KUKA
для полки и цвета также дал 0/50. Эти результаты сохранены отдельно и не подменены
новыми. SR промежуточных curriculum-состояний не включён в итоговую таблицу.

## Инфраструктура

- Все восемь переносимых XML компилируются и имеют рабочую исходную позу.
- 48 автоматических тестов проходят локально и в Docker без сети.
- Физический контроллер выполнил 24/24 base и 24/24 advanced эпизода; это проверка
  достижимости и контактов, а не результат обученной политики на advanced.
- Оценщик изолирует ошибки артефактов; source/hash, split и интерфейсы проверяются.
- Все 64 комбинации оценщика проверены с реальными артефактами на двух шагах:
  три BC-поля здесь используют один пилот; это проверка интерфейсов, не качества.
- Чистый студенческий экспорт прошёл 37 публичных тестов; шесть банков совместимы
  со сценами, один реальный PPO smoke из экспорта выполнил 32 шага и обновил веса.
- Студенческая поставка экспортируется по allowlist, без `reviewer/`, истории git
  и закрытых параметров. Публичные тесты запускаются отдельно в экспорте.

## Пределы выводов

Проверена одна итоговая цепочка обучения на каждую пару; 50 episode seeds не
заменяют несколько независимых seeds обучения. Повторная полная сходимость на
другом оборудовании не измерялась. Высокий base SR не доказывает робастность
на всём диапазоне advanced. Для BC не выполнена студенческая матрица абляций и
аугментаций — подготовлены задания и инфраструктура, а короткий пилот подтверждает
работоспособность обучения, экспорта и инференса на настоящих успешных RL-данных.

## Воспроизведение

```bash
MUJOCO_GL=osmesa python -m pytest -q
MUJOCO_GL=osmesa python -m reviewer.check_scenes --out runs/physical_checks.json
python -m physical_ai.train_curriculum --recipe configs/ppo_calibrated.json \
  --target ur5e/cup_plate --out runs/reproduction
MUJOCO_GL=osmesa python -m reviewer.validate_expert \
  --robot ur5e --task cup_plate \
  --checkpoint runs/reproduction/experts/ur5e/cup_plate/last.zip \
  --out runs/validation/ur5e_cup_plate --seed 120000
python -m reviewer.export_students dist/physical-ai-student --zip
```

Повторите target/validator для всех восьми пар. Используйте новые output-каталоги.
Архив с восемью экспертами, данными и BC-пилотом находится в приватном черновике
[релиза](https://github.com/dpaleyev/physical-ai-final-project/releases); его нельзя
выдавать студентам вместо задания. `SHA256SUMS.json` проверяет содержимое архива.
