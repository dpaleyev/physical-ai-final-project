# Финальный проект Physical AI: от RL-эксперта к робастной визуальной политике

Ваша задача — самостоятельно пройти весь пайплайн для новых роботов: обучить
RL-экспертов, собрать демонстрации, обучить BC и исследовать его ограничения.
Готовая инфраструктура снимает техническую работу с MuJoCo, но не выбирает за вас
эффективную конфигурацию обучения, архитектуру улучшенной модели и метод робастности.

## Матрица задач

| ID | Задача | Условие успеха |
|---|---|---|
| `cup_plate` | Перенести чашку в тарелку | Чашка стоит внутри целевой области тарелки |
| `cup_shelf` | Поставить кружку на полку | Кружка устойчиво стоит на поверхности полки |
| `swap` | Поменять две кружки местами | Каждая кружка стоит около исходной позиции другой |
| `sort` | Разложить кружки по тарелкам нужных цветов | Все три кружки стоят в тарелках соответствующих цветов |

Каждая задача выполняется для `ur5e` и `iiwa14`: **8 независимых RL-политик и
8 BC-моделей для каждого исследуемого варианта**. Общую модель для нескольких задач
можно исследовать дополнительно, но она не заменяет обязательную матрицу.

Объекты должны быть отпущены, находиться в целевой области, сохранять вертикальную
ориентацию и малую скорость не менее восьми управляющих шагов подряд. Точные допуски
открыты в `physical_ai/env.py`. При обмене учитывается идентичность кружек, при
сортировке — соответствие цветов. Близость захвата к цели сама по себе не является успехом.

## 0. Изучите среду

Выполните быстрый старт из README, откройте все восемь сцен. Используйте
`MUJOCO_GUIDE.md` и `physical_ai.scene_tools` для изучения именованных элементов.

Зафиксируйте в отчёте:

- наблюдения и действия, частоту управления и горизонт эпизода;
- различия кинематики роботов и работу готового контроллера;
- условия успеха и возможные причины неудачных эпизодов.

Действие имеет четыре компоненты в диапазоне [-1,1]: приращения целевой позиции
захвата XYZ и команда пальцев (-1 закрыть, +1 открыть). Масштаб XYZ — 0.018 м за
управляющий шаг; частота — 20 Гц. Готовый IK-контроллер переводит это в суставные
цели. Захват физический: предмет не приклеивается и не переносится телепортацией.

RL получает привилегированное состояние. Визуальная BC-политика получает RGB 84×84;
расширенный вариант дополнительно получает положения и скорости суставов робота
и пальцев. Координаты объектов и целей из симулятора подавать BC запрещено.

## 1. Обучите восемь RL-экспертов

Изучите `physical_ai/rl.py`, `physical_ai/env.py` и `configs/ppo_starter.json`.
Последний файл — описание исходных параметров; команда ниже задаёт их явно.
Архитектуру PPO писать с нуля не нужно. Определите бюджет, число сред, параметры
PPO и стратегию обучения. Исходные значения не гарантируют сходимость.

```bash
python -m physical_ai.rl --robot ur5e --task cup_plate \
  --out runs/ur5e/cup_plate/rl --total-steps 2000000 --n-envs 4 --seed 0
python -m physical_ai.evaluate --robot ur5e --task cup_plate --kind rl \
  --checkpoint runs/ur5e/cup_plate/rl/last.zip \
  --episodes 50 --seed 50000 --out runs/ur5e/cup_plate/rl_eval.json
```

При необходимости используйте последовательные стадии `--reward-stage reach`,
`lift`, `place`, продолжая обучение через `--resume PATH/last.zip` в новом `--out`.
Последняя стадия и итоговая оценка должны относиться к полной задаче `place`.
Промежуточная награда — инструмент обучения, а не критерий выполнения задания.
Можно менять её или curriculum в своей ветке; итоговый оценщик использует исходную среду.

Сохраняйте конфигурации, кривые, seeds и результаты независимых rollout.
Проверьте, что политика действительно решает задачу, прежде чем массово собирать
демонстрации. Сравните минимум две настройки RL на одной паре робот × задача.
Повторите успешную процедуру для всей матрицы.

Не заменяйте обучение PPO дистилляцией скрипта с последующим переименованием файла.
Любые дополнительные демонстрации или pretraining указывайте отдельно; нужен
воспроизводимый этап RL-обновлений и его оценка.

## 2. Соберите данные RL-политиками

```bash
python -m physical_ai.data --robot ur5e --task cup_plate \
  --checkpoint runs/ur5e/cup_plate/rl/last.zip --out data/ur5e/cup_plate/train \
  --episodes 100 --seed 1000 --max-attempts 500
python -m physical_ai.data --robot ur5e --task cup_plate \
  --checkpoint runs/ur5e/cup_plate/rl/last.zip --out data/ur5e/cup_plate/val \
  --episodes 20 --seed 10000 --max-attempts 100
```

100/20 эпизодов — стартовый размер эксперимента, а не гарантированно достаточный
датасет. Обоснуйте выбранный объём. По умолчанию сохраняются успешные эпизоды;
долю отброшенных попыток тоже нужно анализировать. `--include-failures` разрешён
для отдельного эксперимента. Сбор ограничен числом попыток и сохраняет журнал ошибок.

Один NPZ содержит эпизод: `rgb`, `proprio`, `actions`, `dones`, `metadata`.
Наблюдение с индексом t записывается **до** выполнения действия t. Метаданные
содержат seed, параметры сцены, результат и SHA256 исходного RL-чекпоинта.
Сохраняйте NPZ и `manifest.json` вместе.

Разделяйте выборки целыми эпизодами. Не смешивайте соседние кадры одного эпизода
между train и validation. Для итогового тестирования используйте отдельные seeds.
Нормализация вычисляется только по train. Укажите объём в эпизодах и переходах,
долю успехов эксперта и частоты команд захвата.

## 3. Обучите BC и выполните сравнения

Запустите RGB-baseline на каждой из восьми пар:

```bash
python -m physical_ai.bc --train-dir data/ur5e/cup_plate/train \
  --val-dir data/ur5e/cup_plate/val --out runs/ur5e/cup_plate/baseline \
  --epochs 30 --seed 0
python -m physical_ai.bc --train-dir data/ur5e/cup_plate/train \
  --val-dir data/ur5e/cup_plate/val --out runs/ur5e/cup_plate/proprio \
  --epochs 30 --use-proprio --seed 0
python -m physical_ai.evaluate --robot ur5e --task cup_plate --kind bc \
  --checkpoint runs/ur5e/cup_plate/proprio/best.ts \
  --episodes 50 --seed 50000 --out runs/ur5e/cup_plate/bc_eval.json
```

Для GPU добавьте к обучению BC `--device cuda`, установив соответствующую сборку
PyTorch. Исходный CNN небольшой и работает без загрузки предобученных весов.
Вы можете изменить энкодер, функцию потерь, добавить историю наблюдений или иной
механизм. Сохраняйте контракт инференса и экспорт модели для проверки.

Обязательные сравнения:

1. RGB-only и RGB + проприоцепция на одинаковых данных для всех восьми пар.
2. BC и RL-эксперт: отдельно отметьте преимущество эксперта в наблюдениях.
3. Минимум на одной задаче **для обоих роботов** — абляция объёма данных
   (например, 25% и 100% эпизодов) при одинаковых остальных условиях.

Используйте минимум три training seeds для выбранной подробной абляции. Остальные
запуски должны быть воспроизводимыми хотя бы с одним seed. На итоговой оценке
используйте минимум 50 эпизодов на конфигурацию и одинаковые evaluation seeds у
сравниваемых политик. Основная метрика — success rate с доверительным интервалом;
MSE, длина успешного эпизода и типы ошибок — дополнительные показатели.

`best` выбирается по validation MSE. Проверьте самостоятельно, насколько этот выбор
согласуется с rollout-качеством; тестовые сцены нельзя использовать для выбора модели.

## 4. Исследуйте робастность

У среды много изменяемых параметров: атрибуты тел и геометрий, материалы, физические
свойства, освещение, камера. Полный список имен доступен через инспектор;
допустимые JSON-атрибуты описаны в руководстве. Выберите собственные осмысленные
вариации, объясните, почему задача после изменения остаётся разрешимой.

Сначала изменяйте один фактор, затем исследуйте сочетания. Заранее отделите
вариации для обучения, выбора гиперпараметров и локальной проверки. Выберите
не менее трёх семейств изменений и проверьте все восемь пар. Не меняйте правила
задачи или критерий успеха, чтобы улучшить метрику.

Сравните с исходной сценой, покажите падение success rate, интервалы и характерные
неудачи. Достаточно таблиц, графиков и нескольких видео; важен проверяемый вывод.

## 5. Обучите BC с аугментациями

Создайте собственный банк параметров сцен — JSON-массив объектов формата
`configs/scene_example.json`. Соберите новые демонстрации с помощью RL-экспертов:
передайте коллекционеру `--scene-bank PATH`. Проверяйте успех эксперта отдельно
на изменённых сценах. При необходимости дообучите эксперта и укажите это в отчёте.

Различайте два механизма:

- преобразования входных изображений с сохранением корректности действия;
- изменения физического состояния среды, после которых нужна новая траектория
  эксперта или обоснованное преобразование меток.

Нельзя переместить предмет, оставить прежние действия и считать такую пару
корректной демонстрацией. Не уничтожайте преобразованием информацию, определяющую
правильное действие. Встроенный `--image-augmentation` даёт только простой пример
шума освещения; собственные изменения сцены — обязательная часть исследования.

Обучите робастный вариант для каждой из восьми пар. Сравните его с исходным BC при
одинаковом общем числе демонстраций, либо добавьте контроль с тем же объёмом данных.
Проверьте исходные и отложенные локальные вариации. Улучшение не обязано быть
положительным во всех условиях: объяснённый отрицательный результат тоже результат.

## 6. Сдача и проверка

Скопируйте `submission.example.json` в `submission.json` и укажите реальные пути.
В одной строке матрицы нужны: RL (`last.zip` + `last.json`), RGB-baseline,
BC с проприоцепцией и BC после исследования аугментаций (`best.ts` + `best.json`).
Все пути относительны каталогу сдачи. Шаблон содержит все восемь пар.

В комплект входят:

- код и команды воспроизведения, версии зависимостей и конфигурации запусков;
- checkpoints всех вариантов и соответствующие метаданные;
- восемь наборов данных или доступные организаторам ссылки с контрольными суммами,
  manifest и описанием разбиения;
- логи RL/BC, результаты оценки JSON/CSV, несколько видео;
- `REPORT.md` по шаблону `REPORT_TEMPLATE.md` с абляциями и выводами.

Готовый BC-тренер автоматически экспортирует TorchScript. Контракт экспортируемой
модели: `forward(rgb: float32[B,3,84,84], proprio: float32[B,P]) -> float32[B,4]`.
RGB в [0,1], действия в [-1,1]; P=16 для UR5e и P=18 для KUKA. RGB-only модель
принимает второй аргумент, но не использует его. Для архитектуры с внутренним
состоянием добавьте экспортируемый `reset()`; оценщик вызывает его перед эпизодом.

Base-проверка использует опубликованные сцены и новые seeds. Advanced-проверка
использует закрытые варианты сцен с сохранением смысла задач и того же интерфейса.
Конкретные варианты, параметры и seeds не публикуются. Подбирать решение по
результатам закрытой проверки нельзя.

Чек-лист: 8 RL-политик; сбор данных ими; 8 основных BC-экспериментов; сравнение с
baseline; минимальные абляции; исследование робастности; 8 вариантов после
обучения с аугментациями; воспроизводимые артефакты. Готовый запуск без анализа
и самостоятельных экспериментальных решений не завершает проект.
